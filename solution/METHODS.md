# Methods and Documentation

ASME CIE 2026 Student Hackathon, Problem 1 (Siemens GeoCAiM)

This document describes how our solution works, why it is built the way it is,
what we measured, and where it fails. It is written for the Round 2 criteria:
originality, effectiveness and efficiency, documentation quality,
generalizability, and scientific rigor.

## Terms used in this document

We spell these out once here because several are used throughout.

* **CNC**: computer numerical control, the machine type this problem targets.
* **CAM**: computer-aided manufacturing, the software category that produces
  machining plans. The dataset was generated with Siemens NX CAM.
* **BRep**: boundary representation, the exact mathematical description of a
  solid's faces, edges, and vertices. Supplied as a STEP file.
* **STEP**: Standard for the Exchange of Product model data, the neutral CAD file
  format (`.stp`) used for the part geometry.
* **IPW**: in-process workpiece, the shape of the partly machined block after a
  given operation.
* **STL**: the triangle mesh file format used to deliver each IPW.
* **NC code**: numerical control code, the instruction list a machine executes.
  Delivered as `.ptp` files, also called G-code.
* **IoU**: intersection over union, the volume overlap measure used to score the
  medium and hard tiers.
* **o1 and o2**: the main and sub operation labels defined by the contest
  vocabulary, for example `hole_making` and `DRILLING`.

## 1. Summary of what we built

Given a part as a boundary representation, our pipeline predicts the full
machining plan: the ordered sequence of operations, the in-process workpiece
after each one, the tool used, and the numerical control code.

The pipeline has five stages.

1. A STEP reader that parses the boundary representation directly.
2. Feature recognition that finds holes, pockets, chamfers, and corner blends.
3. Plan prediction, which is part learned and part rule based.
4. Geometry generation, which produces the in-process workpiece meshes and the
   numerical control code from one shared engine.
5. A local reimplementation of the contest rubric, used to score every change.

Current score on 400 parts that no model was trained on: **52.25 out of 100**.
Reported in the rubric's own three categories:

| Category | Points available | Ours | Share |
|---|---:|---:|---:|
| Easy, operation sequence | 20 | 17.53 | 88 percent |
| Medium, in-process workpiece | 35 | 23.02 | 66 percent |
| **Hard, tools and tool paths** | **45** | **11.70** | **26 percent** |
| Total | 100 | 52.25 | |

The hard category is defined in the rubric as 45 points split into two
sub-scores, tool selection at 20 and tool path geometry at 25. We report them
separately elsewhere in this document because they fail for entirely different
reasons and need different work, but they are one category for scoring.

Within the hard category, tool selection stands at 10.91 of 20 with the tool
*type* already correct on every aligned operation, so the whole loss there is
diameter. Tool path geometry stands at 0.79 of 25, where the scoring engine is
validated but the path generator is not yet adequate. Nearly all of our missing
points sit in this one category.

**A second, independent check on the 52.25.** The 400 parts above are one fixed
slice of held-out data (part index 8,000 to 8,399), reused across every
comparison in this project so before-and-after measurements stay paired. The
other 1,600 held-out parts (8,400 to 9,999) were never touched by any model or
configuration decision until this check, and scoring them separately gives:

| | 400-part slice | 1,600-part reserve | All 2,000 combined |
|---|---:|---:|---:|
| Easy | 17.41 | 17.20 | 17.24 |
| Medium | 23.02 | 22.72 | 22.78 |
| Tools | 10.96 | 10.81 | 10.84 |
| **Total, of 75** | **51.40** | **50.73** | **50.87** |
| 95 percent confidence interval | [49.69, 53.08] | [49.89, 51.60] | **[50.10, 51.65]** |

Every tier's difference between the two slices crosses zero under an unpaired
bootstrap, so the 400-part figure was not a favourable draw. Combining all
2,000 gives a tighter estimate at almost the same value, **50.87 of 75**, or
**51.7 of 100** with the path tier added, next to the original **52.25 of 100**
from the 400-part slice alone. We report both rather than replace one with the
other: the 400-part figure is what every design decision in this document was
actually measured against, and the 2,000-part figure is the more precise
estimate of where that decision-making landed.

The submission for the released test set is generated by
`scripts/predict_test_set.py`. It covers all 30 test parts with no failures, and
all 120 artifacts pass the official validator. Generation takes 9.5 seconds in
total, about 0.3 seconds per part.

### A note on the test set

Two things about the released test data are worth recording, because they are
exactly what a generalizability claim should be tested against.

One part, `featured_part_22222`, ships with a note saying to infer it without any
images, and its folder contains no images at all. Our pipeline reads only the
boundary representation and never opens a render, so this part is processed the
same way as every other. We had already concluded from measurement that the
images cannot supply information the boundary representation lacks; see
section 11.

That same part is also outside the training distribution in two respects. It has
16 holes where the training corpus contains at most 6 per part, and its block is
32 millimetres tall where the corpus range is 50 to 150. Our recogniser and both
classifiers handle it without error, but we would expect our predictions there to
be less reliable than on the other 29, because no comparable part existed in
training. We flag this rather than hide it.

Across all 30 test parts the block dimensions otherwise sit inside the corpus
ranges: lengths 202 to 498 millimetres, widths 200 to 496, heights 32 to 150.
Hole diameters reach 38.5 millimetres against a corpus range of 5 to 50.

### What we expect to score on the test set, and why it is lower

The test folders contain no ground truth, so we cannot measure ourselves on them.
Our held-out figure of 51.40 out of 75 is the natural estimate, but it would be
misleading to quote it without an adjustment, for two reasons. This reweighting
uses the original 400-part slice specifically, because the complexity buckets
below were built from it; we have not recomputed them against the fuller
2,000-part figure from section 5, so treat this section's arithmetic as
relative to 51.40, not to 50.87.

The test parts are harder than our held-out sample. They average 13.27 predicted
operations per part against 9.21, and 3.77 recognised holes against 2.29. That is
1.44 times the operation count.

Our score falls as parts get more complex. Grouping our 400 held-out parts by
predicted operation count gives mean scores of 56.84 out of 75 for parts with
eight operations or fewer, 47.35 for nine to thirteen, 43.29 for fourteen to
twenty, and 47.86 above twenty. The correlation between operation count and score
is minus 0.329.

Reweighting our held-out results to the complexity mix actually present in the
test set gives **47.69 out of 75 instead of 51.40**, a drop of 3.71 points.
Adding the tool path tier at roughly 0.8 out of 25, our honest expectation for
the released test set is about **48 out of 100**, not the 52 that our unweighted
held-out figure would suggest.

We report the lower number because it is the one we believe.

## 2. Approach, and how it differs from prior work

### Related work

The dataset paper cites two closely related lines of research. MFCAD and
MFCAD++ (Cao et al. 2020, Colligan et al. 2022) label boundary representation
faces with machining features, but they stop at feature recognition and contain
no operation sequence, tool assignment, or intermediate geometry. DeepMS
(Maqueda, Rosen, and Melkote 2025) is the only prior work that predicts both the
machining sequence and the in-process workpiece, and it does so from voxel
representations at roughly one voxel resolution. MP-GFormer (Elhambakhsh et al.
2025) frames process planning as dynamic graph transformer learning over
geometry.

### There is no published baseline on this dataset

We looked for a number to compare against and could not find one, so we want to
be explicit rather than imply a comparison we cannot make.

The MachinePlan-10K paper is a dataset description and reports no model results.
MP-GFormer reports improvements of 24 percent on main operation prediction and 36
percent on sub-operation prediction, but those are relative gains against unnamed
baselines on an unnamed synthesized dataset, with no absolute figures, so they
cannot be placed alongside ours. DeepMS works on its own corpus of 180,000 voxel
parts, which is a different representation of a different dataset.

MachinePlan-10K was published in July 2026, and this competition appears to be
its first public evaluation. We therefore have no external benchmark, and our
comparisons are internal: hand written rules against learned models on identical
held-out parts, and null baselines such as submitting the unmachined stock.

One external reference point does exist and it is useful. The dataset paper
reports that generated parts were accepted only if more than 99 percent of the
material was removed and the final intersection over union exceeded 0.999, with
10,000 of 11,416 parts passing, an 87.6 percent yield. The medium tier's top band
is also 0.999. So that threshold is not arbitrary: it is the bar the generator
held itself to, and it is what a correct simulation produces. Our mean of 0.9909
sits below it, and section 9 explains by how much and why.

### How our approach differs

Our approach differs in three ways that follow from the problem rather than from
a preference for any particular method.

**We work from exact geometry, not voxels.** DeepMS operates on voxel grids. The
medium tier here is scored with an intersection over union threshold of 0.999 for
full marks. We measured that voxel intersection over union at a one millimetre
pitch on a part 200 to 500 millimetres across resolves only to about one part in
a thousand, which straddles that exact threshold rather than resolving it. So we
parse the boundary representation and use exact mesh booleans throughout.

**We treat the medium and hard tiers as one problem.** The rubric scores a tool
path by comparing the volume it sweeps against the difference between the
in-process workpiece before and after the operation. That is an identity:

```
swept volume of operation k  =  IPW(k-1) minus IPW(k)
```

So a single removal-volume engine produces both the medium tier meshes and the
hard tier paths. Sixty of the hundred available points share one backbone
instead of needing two separate solutions.

**We decide learned versus rule based per feature type, by measurement.** This is
the part we consider most original. We did not choose a method up front. For each
of the three feature families we wrote a rule, measured it, then tested whether a
classifier trained on the same inputs could beat it on held-out parts. The three
families gave three different answers, and we kept whichever won.

### What we learned about the data before modelling

Two structural facts changed the shape of the problem, and both came from
analysis rather than training.

The main label `o1` carries no independent information. Cross-referencing the
frequency tables in the dataset paper, `AREA_MILL` occurs 20,067 times and so
does `mill_contour`; `FLOOR_WALL` and `mill_planar` are both 18,560; and the five
hole-making sub-labels sum to exactly 53,075, the `hole_making` total. The
sub-label determines the main label with certainty, so a model only needs to
predict `o2`. That removes an entire error mode before any training happens.

A plan is not sorted, it is grouped by tool. We tested three orderings across all
10,000 parts. "Chamfers, then pockets, then holes" holds for 54.45 percent.
Sorting by the NX order group holds for 27.93 percent. But "each tool occupies
one contiguous block" holds for 70.55 percent, and the metadata field
`tool_changes` equals the number of tool blocks minus one for 10,000 parts out of
10,000, with no exceptions. The plan is tool change minimisation subject to
precedence constraints. Because 97.65 percent of those blocks carry a single
label, the easy tier's real target is about 4.5 label runs per part rather than a
sequence of up to 38 tokens.

## 3. The models, and the evidence for them

### Hole operation chains

Across 1,120 holes matched to their operations by position, only 14 distinct
operation chains occur. Predicting a hole's operations is therefore a 14-way
classification rather than open-ended sequence generation.

We first wrote rules from mined thresholds. They reached 0.374 chain accuracy. A
gradient boosted classifier over the same geometric inputs reached **0.970** on
6,757 holes from 2,519 parts never used in training.

| Predictor | Chain accuracy | Mean absolute operation count error per hole |
|---|---:|---:|
| Majority class | 0.302 | not applicable |
| Hand written rules | 0.374 | 0.674 |
| Gradient boosting | **0.970** | **0.040** |

The rules scored zero on the single most common chain, plain `DRILLING`, because
they always added a spot drill below 20 millimetres diameter. They also scored
zero on two chains we had tried and failed to characterise by hand.

### Block ordering

Our planner originally emitted a fixed order of chamfers, then pockets, then
holes. Measured across all 10,000 parts, that order is correct for 26.5 percent.
The most common order is holes, then chamfers, then pockets, at 34.1 percent. We
had been using the second most common one.

A classifier over part level geometry predicts the order with **0.896** accuracy
against 0.349 for always guessing the most common. Adding it was worth 5.87
points, measured as a paired comparison over 400 held-out parts, with every tier
significant.

### Pockets stayed rule based, and the failure was informative

We applied the same recipe to pocket operation counts. The classifier scored
0.859 against 0.865 for the trivial rule of one operation per recognised floor.
It lost, so we did not ship it. Its recall on the cases that mattered was 0.091
and 0.000. The training script refuses to save a model that does not beat the
current rule by a stated margin, so this was caught automatically rather than by
judgement.

That failure was worth more than a marginal win would have been. For holes the
problem had been that a real boundary existed but was not findable by hand. For
pockets there was no signal in the recognised geometry at all, which pointed us
upstream to the recognition code, where we later found a genuine bug.

### Chamfers stayed rule based because a rule is already exact

One `AREA_MILL` operation per recognised slanted face gives the exactly correct
count on 200 parts out of 200. There is nothing to learn.

## 4. How the models were trained

Both shipped models are gradient boosted classifiers, fitted by us from the
competition dataset alone. This section describes the protocol in enough detail
to repeat it.

### Building the training tables

The dataset gives an operation sequence per part but does not say which operation
belongs to which feature. We recover that by position. Every drilling operation
names its X and Y in the machine code, and feature recognition gives every hole
its centre, so matching the two assigns operations to individual holes. That
matching succeeds for **98.6 percent of holes and 99.2 percent of hole
operations**, which is what makes per-feature training possible at all.

The result is 22,500 holes, each carrying ten geometric inputs and one label: the
ordered chain of operations that machined it. Across the corpus only fifteen
distinct chains occur, so predicting a hole's operations is a classification
problem with a small label set rather than open-ended generation.

The block ordering table is built the same way at part level: eleven part
geometry inputs, and the order in which the three feature families appear.

### What is allowed as an input

Only values derived from the boundary representation, because that is all that
exists at inference. Operation labels, meshes, machine code, and the dataset
metadata are targets and never inputs. This is easy to get wrong and would
produce a model that scores well on a split and means nothing.

### The split

Deterministic on the part number. Parts numbered below 8,000 are used for
training; parts numbered 8,000 and above are never touched. That makes a held-out
evaluation honest by construction rather than by argument, and it means anyone
can verify which parts a model saw.

The split is by **part**, never by feature. Holes on one part share a block, a
feature mix, and a tool set, so splitting by hole would put near duplicates on
both sides and report an inflated number.

### The baseline is the rule, not chance

Each model is compared against the hand-written rule it would replace, not
against a majority class. A model that cannot beat the rule already in the
pipeline is not worth shipping, and comparing against chance would hide that.
The training scripts enforce this: they refuse to save a model that does not beat
its rule by a stated margin. That is how the pocket model was rejected
automatically rather than by judgement.

### Why gradient boosting, and not another model family

`HistGradientBoostingClassifier` was chosen at the start of the project and
never checked against an alternative. That is a real gap, since a modelling
choice this central deserves a comparison, not an inherited default. We closed
it with the same disciplined split as the hyperparameter sweep below: six
families fit on parts 0-6,999, selected by accuracy on parts 7,000-7,999, so
choosing a family cannot see the parts-8,000-and-up test set either.

| Model | Hole chain, validation | Block order, validation |
|---|---:|---:|
| Majority class | 0.2613 | 0.3570 |
| Logistic regression | 0.6967 | 0.8650 |
| k-nearest neighbours, k=15 | 0.6893 | 0.7700 |
| Random forest, 300 trees | 0.8527 | 0.8947 |
| Small neural network (two hidden layers) | 0.7652 | 0.8776 |
| Single decision tree | 0.9442 | 0.8215 |
| **Gradient boosting, shipped** | **0.9692** | **0.9016** |

Gradient boosting wins outright on both tasks, so no refit-and-recheck against
the untouched test set was needed the way the hyperparameter comparison below
required; held-out test accuracy reproduces the figures already reported
elsewhere, 0.9701 and 0.8968.

The pattern across both tables is as informative as the winner. Tree-based
methods dominate linear and distance-based ones on both tasks, and a single,
completely undocumented decision tree alone reaches 0.9442 on hole chains, five
points under gradient boosting but thirty points over logistic regression. Our
own rule-based components are threshold logic on these same features, for
example a diameter ratio or a depth range with a hard cutoff, so the true
decision structure here is a set of axis-aligned thresholds, which is exactly
what a tree represents and a linear or nearest-neighbour model does not.
Boosting improves on a single tree by correcting its errors sequentially;
random forest's row and feature subsampling helps less here, plausibly because
ten input features and several rare classes leave little for subsampling to
exploit.

### Hyperparameters, and whether we tuned them

Both models were shipped close to scikit-learn's defaults for
`HistGradientBoostingClassifier`: `learning_rate=0.1` and `max_leaf_nodes=31` are
the library defaults, unchanged. We raised `max_iter` from 100 to 300 on both,
and added `l2_regularization=1.0` on the hole-chain model, without a documented
search behind either choice. That is a real gap and worth stating plainly rather
than leaving silent.

We closed it with a small grid search, run properly rather than casually: a
third split, carved out of the *training* range only (parts 0-6,999 fit, parts
7,000-7,999 validate), so the parts-8,000-and-above test number every other
figure in this document rests on was never touched by model selection.

| | learning rate | leaf nodes | L2 | fit / validate / test |
|---|---:|---:|---:|---|
| Hole chain | {0.05, 0.1, 0.2} | {15, 31, 63} | {0, 1.0} | 13,690 / 2,044 / 6,757 |
| Block order | {0.05, 0.1, 0.2} | {15, 31, 63} | {0, 1.0} | 6,111 / 874 / 3,015 |

**Block order:** the best configuration on the validation split matched the
shipped one exactly on the held-out test set, 0.8968 either way. No gain, no
loss. The current configuration stands.

**Hole chain, and the more interesting result.** The best configuration by
validation accuracy (`learning_rate=0.05, max_leaf_nodes=15, l2=0`) scored 0.9770
on validation against the shipped configuration's 0.9692, a seemingly clear
win. Refitting both on the full training range and scoring on the untouched test
set flipped the result: the shipped configuration held at **0.9701**, while the
validation winner fell to **0.9415**, a loss of nearly three points.

The validation split has 2,044 rows spread across fifteen classes, several of
them rare, so a configuration that fits its particular noise can look better
there and generalize worse everywhere else. This is the same lesson as F-050,
applied to model selection instead of feature engineering: a comparison on too
little data is not evidence, and here it would have actively misled us into
shipping a worse model. The originally chosen values, arrived at without a
formal search, turned out to be the right call, and now that is measured rather
than assumed.

### Data filtering, disclosed

Nine holes, 0.04 percent of 22,500, belonging to three operation chains occurring
fewer than five times in the whole corpus, were removed from **both** halves of
the split. Such chains cannot be learned or fairly evaluated, and a class with a
single member breaks the stratified validation split the gradient booster uses
internally. Removing them from training alone would have flattered the reported
accuracy.

### Determinism

The whole pipeline is deterministic: the same STEP file produces byte identical
output on every run. The learned components do not change this, because a
gradient boosted classifier is a fixed function once fitted. Its random seed
decides which trees get built during training and has no effect on prediction
afterwards.

This is covered by tests rather than asserted. `tests/test_determinism.py`
fingerprints the operation labels, the tool choices, every mesh volume and face
count, and every line of emitted machine code, then checks that two runs agree.
It also checks that different parts produce different fingerprints, so the test
cannot pass vacuously.

## 5. Validation

### What the score is, exactly

Every number in this document is a score out of 100, so it is worth stating how
those 100 points are assembled. The rubric does not use a continuous formula. It
maps each continuous metric onto points through a lookup band, which makes the
total a step function of the underlying geometry. That property shaped which
problems we worked on, so we treat it as a modelling fact rather than a scoring
detail.

The total is the sum of five banded terms:

| Term | Metric it reads | Budget |
|---|---|---:|
| Sequence similarity | normalised Levenshtein distance between predicted and true operation sequences | 10 |
| Operation set agreement | multiset F1 score over operation labels | 10 |
| Workpiece geometry | mean intersection over union across in-process workpiece meshes | 35 |
| Tool selection | mean over operations of a tool score, which is zero unless the tool type matches exactly, and otherwise reads relative diameter error | 20 |
| Tool path geometry | intersection over union, plus overcut, plus undercut, on the swept volume | 25 |

The bands themselves are steps, not slopes. The workpiece term is the clearest
case:

| Mean intersection over union | 0.999 and above | 0.99 | 0.98 | 0.95 | 0.90 | below 0.90 |
|---|---:|---:|---:|---:|---:|---:|
| Points | 35 | 25 | 20 | 15 | 10 | 0 |

Three consequences followed directly, and each one redirected effort.

Below 0.90 the term pays nothing at all. Early in development our geometry was
accurate but our operation counts were wrong, which put whole parts under that
floor and zeroed a 35 point category. Fixing counts was therefore worth more than
any geometry work, which is why the first two iterations touched no geometry.

The final band is narrow and expensive. Our mean is 0.9909, which sits just
inside the 0.99 band and earns 25. Reaching 0.999 earns 35. So the last 0.008 of
overlap carries ten points while the preceding 0.09 carried five. A mean alone
hides this, which is why we report the share of parts above each threshold rather
than the average.

A wrong tool type zeroes its operation outright, no matter how close the
diameter. We therefore track tool type accuracy and diameter error as two
separate quantities. Type accuracy is 100 percent on held-out parts, so all of
our remaining tool loss is diameter.

One caveat on the two budgets. The rubric's tool selection section is titled 20
points but its table tops out at 10, and its tool path section is titled 25 points
but its three tables sum to 30. We score the tables exactly as printed and then
rescale to the stated section budget, by a factor of 20 over 10 and 25 over 30
respectively. This is our reading, not the rubric's instruction, so we made it a
switchable option rather than a silent assumption. It is the first of the two
questions we raise in section 9.

### The four layers

We used four layers, and two rules that each caught real defects.

**Unit tests against closed forms, not stored values.** A cylinder of radius r
and height h dragged a distance L must sweep a volume of pi times r squared times
h, plus 2 r L h. A test that merely pinned current behaviour would have allowed a
systematic error through. There are 96 tests.

**Feature recognition against published statistics.** The dataset paper reports
corpus figures our recogniser never sees.

| Metric | Ours | Paper |
|---|---:|---:|
| Holes per part | 2.283 | 2.330 |
| Hole diameter mean, millimetres | 16.97 | 17.47 |
| Hole diameter range, millimetres | 5.0 to 50.0 | 5.0 to 50.0 |
| Blind hole share | 0.502 | 0.502 |
| Block length, width, height means | 345, 341, 97 | 350, 351, 100 |

**Geometry against ground truth.** For one real chamfering operation, three
independently derived quantities agree: the metadata reports 53,100.9 cubic
millimetres removed, the mesh difference gives 53,101.0, and our swept volume
clipped to the stock gives 53,101.6. Scored the way the rubric scores it, that is
an intersection over union of 0.99997 with overcut and undercut both under 0.0001.

**End to end on held-out parts, with confidence intervals.** Every configuration
choice is now decided by a paired comparison over 400 parts with a bootstrap
interval, because we found that several earlier decisions had been made on
differences smaller than the noise.

The comparison itself, stated precisely, is a percentile bootstrap on the
per-part paired difference:

```
delta_i = score_i(new) - score_i(old)
CI_95   = [ percentile_2.5(mean(delta*)), percentile_97.5(mean(delta*)) ]
```

Resample the per-part differences with replacement 5,000 times, take the mean
of each resample, and keep the middle 95 percent of those 5,000 means. A change
is treated as real only if that entire interval sits above zero; if it crosses
zero, it is dropped. This is `bootstrap_ci` in `scripts/evaluate.py`, called on
the same 400 parts for every comparison in this document.

We use a bootstrap rather than a paired t-test because a t-test assumes the
underlying differences are roughly normal, and ours are not: the rubric scores
in bands (section 5 above), so a single part's score jumps between a small set
of fixed values rather than varying smoothly. The bootstrap makes no assumption
about that shape, which matters here, not as a formality.

**Where this changed our own conclusions.** Measured naively on 20 parts by
comparing two averages, our strongest change looked worth +3.31 points.
Measured this way, on 150 parts, pairing each part against itself, it was worth
**+8.14**, with a 95 percent interval of [+5.34, +11.06] entirely above zero.
The careful method did not just confirm the result, it showed the naive one had
understated our best change by more than half.

Two disciplines are worth stating explicitly.

We split by part, never by hole. Holes on one part share a block, a feature mix,
and a tool set, so splitting by hole would place near duplicates on both sides of
the split. The split is also deterministic on the part number: everything below
part 8,000 trains, everything at or above it is never touched. That makes a
held-out evaluation honest by construction rather than by argument.

We quote the held-out number, not the in-sample one. Scoring parts inside the
training range gives 36.85 where held-out parts give 31.22, measured at the same
point in development. That gap of about 5.6 points is a fair estimate of how
optimistic in-sample evaluation is on this problem.

## 6. Computational efficiency

| Stage | Cost |
|---|---|
| Reading the 5.2 gigabyte dataset | Streamed from inside the zip archive, never extracted |
| Indexing 10,000 parts | 3.2 seconds |
| Parsing one STEP file | Milliseconds; files average 25 kilobytes |
| Full pipeline for one part | About 1.8 seconds including mesh booleans |
| Scoring 400 parts end to end | Under 2 minutes for the easy, medium, and tool tiers |
| Training the hole chain classifier | Under a minute on 15,734 holes |

Two efficiency decisions are worth explaining.

**We never extract the dataset.** The archive is 5.2 gigabytes and expands to an
estimated 25 to 30 gigabytes. The development machine had 35 gigabytes free. We
read part files on demand through the zip central directory, which keeps the
footprint at 5.2 gigabytes and costs nothing measurable in speed.

**We compute swept volumes exactly rather than by sampling.** Every cutting tool
in this problem is a convex solid of revolution: an endmill is a cylinder, a
drill is a cylinder with a conical point, a chamfer mill is a truncated cone on a
shank. For a convex body translated along a straight segment, the swept region is
exactly the convex hull of the body at the two endpoints. So each move is one
hull rather than many stamped tool positions. On a real operation that is 272
hulls instead of about 4,944 placements, and the result is exact rather than
approximate. Convexity is asserted directly in the test suite, because the
identity fails for any tool with an undercut profile.

**No CAD kernel is required.** We measured the surface types in the corpus before
taking on a dependency. Every surface is either a plane (74.79 percent) or a
cylinder (25.21 percent). There are no splines, cones, or tori. A targeted reader
of about 300 lines covers it, with zero parse failures across 400 parts. This
avoids a roughly 400 megabyte OpenCascade dependency. A helper called
`surface_type_census` exists so the assumption can be rechecked on new data.

## 7. How to reproduce

Requirements are numpy, scipy, trimesh, manifold3d, shapely, rtree, networkx,
scikit-learn, joblib, and pytest. Python 3.12.

```
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt

python scripts/download_dataset.py          # resumable, checksum verified
python scripts/build_hole_dataset.py        # extract training table
python scripts/train_hole_classifier.py     # fit and save, only if it beats the rules
python scripts/train_block_order.py         # fit and save the block-order model
python scripts/run_baseline.py --offset 8000    # generate a submission and score it
python scripts/evaluate.py --offset 8000        # held-out score with confidence intervals
python scripts/predict_test_set.py               # write the test-set submission
python -m pytest tests -q                       # 96 tests
```

`--offset 8000` matters. It restricts evaluation to parts at or above 8,000,
which no model was trained on.

Every analysis in this document has a script that regenerates it. The diagnostic
scripts (`diagnose_counts.py`, `diagnose_pockets.py`, `diagnose_tools.py`,
`diagnose_medium.py`, `sensitivity_alignment.py`, `compare_cut_policies.py`) are
kept in the repository even though they produce no submission output, because
they are the evidence for the design decisions described here.

## 8. Data handling, filtering, and augmentation

The tutorial asks that any filtering or augmentation be reported clearly. Here is
the complete list.

**Filtering applied to training data.** Nine holes, which is 0.04 percent of
22,500, belonging to three operation chains that occur fewer than five times in
the whole corpus, were removed. Such chains cannot be learned or fairly
evaluated, and a class with a single member breaks the stratified validation
split the gradient booster uses internally. They were removed from both the
training and the test halves, not from training alone, so the reported accuracy
is not flattered by quietly dropping hard cases from the test set.

**Filtering applied when scoring.** Consecutive in-process workpiece meshes are
re-triangulated between exports, so their boolean difference contains thin sheets
alongside the material actually removed. We measured sheets as thin as 17
microns spanning up to 92 millimetres. On a large operation this is irrelevant.
On a small one it dominates: for one spot drilling operation the raw difference
was 42.0 cubic millimetres of which the real dimple was 3.3, so the noise was
twelve times the signal. We discard bodies thinner than 0.05 millimetres on any
axis when building a reference volume. The filter is on thickness rather than
volume, because those sheets are thin but not small, and a volume filter keeps
exactly the wrong ones.

**Augmentation used.** None. We identified two valid augmentations and used
neither, because the training data proved sufficient without them. They are
described under future work.

**No augmentation was invalid but tempting.** Uniform scaling would change
feature sizes, which changes tool selection, which changes the labels. It is not
label preserving and we did not use it.

## 9. Generalizability and limitations

### Where we expect the method to hold

The recovered rules are geometric and metric, not identifiers, so they should
transfer to any part built from the same feature vocabulary of pockets, holes,
and chamfers on a rectangular block. Nothing in the pipeline keys on a part name,
an index, or any artefact of how the dataset was ordered.

The feature recogniser is validated against published corpus statistics rather
than against a held-out split of our own making, which is a stronger check
because those statistics were computed independently of us.

### Where we expect it to fail

**Surfaces outside planes and cylinders.** The STEP reader handles the two
surface types present in this corpus. A part with a spline surface would be read
with fewer faces rather than failing loudly. The `surface_type_census` helper
exists to detect this, but it must be run deliberately.

**Non-rectangular stock.** Everything assumes a cuboidal blank.

**Features the dataset excludes.** The dataset itself contains no threaded,
countersunk, or counterbored holes, so we have no evidence about them either.

**Tool paths.** This is our weakest area and we would not claim it generalizes,
because it does not yet work on the training distribution. See below.

**One valid plan per part.** The dataset supplies a single sequence per part
although machining genuinely admits many. A correct alternative plan scores as
wrong. This limits what any method can achieve here, and it means our accuracy
figures measure agreement with one particular CAM system rather than machining
correctness in general.

### Known weaknesses, stated plainly

Our tool path tier scores 0.79 out of 25. The swept volume engine that scores it
reaches about 23.5 out of 25 when fed ground truth operations, tools, and paths,
so the engine is sound and the generation is not. Diagnosing one 15 operation
part showed three separable causes: chamfer paths emit no cutting move because we
have not solved the offset geometry, four operations had a ground truth removal
of zero cubic millimetres after denoising, and pocket clearing paths follow the
floor's bounding box rather than its true outline.

Our medium tier scores 23.00 out of 35, and we believe it is close to the
ceiling this input allows. The reasoning is worth setting out because it is a
limitation of the problem rather than of our implementation.

Operation counts are close to correct, with a mean length ratio of 0.981, so the
remaining error is not counting. We attributed it per feature and found pockets
at 0.979 intersection over union against holes at 0.993 and chamfers at 0.995.
We built three geometry refinements, and all three measured neutral.

We then compared the *finished* part rather than the intermediate states. The
finished part is order independent, since it is the stock minus the union of
everything removed, so comparing it separates what we cut from when we cut it.
The finished part reaches an intersection over union of 0.9965, with 27 of 40
parts above the 0.999 threshold, while the mean across all indices is 0.9909 with
only 31 percent above it. In other words we remove the right material and we
remove it in the wrong order.

Three levels of ordering were then tested. Our family order, meaning chamfers
against pockets against holes, matches the ground truth for 95 percent of parts
on first appearance and 90 percent on the full run structure. Ordering the tool
blocks within a family by descending diameter, ascending diameter, or first use
gave 0.99078, 0.99025, and 0.99088, all within noise of each other. That leaves
the finest level: which individual hole or pocket is machined first inside a
block that uses a single tool.

That ordering is not recoverable from the geometry we are given. We tested
candidate rules across 438 same-tool blocks. Nearest neighbour travel matched
40.2 percent where chance is about 50 percent, sorting by Y matched 37.2 percent
and sorting by X 30.1 percent where chance is about 33 percent. Every candidate
sat at or below chance, and the actual travel was 18 percent longer than a greedy
tour. The order appears to follow the sequence in which features were created in
the original CAD model, which is not present in the boundary representation we
receive.

There is an asymmetry here that is easy to miss. For the easy tier this ordering
is free, because 97.65 percent of tool blocks carry a single operation label, so
permuting features inside a block cannot change the label sequence or the edit
distance. For the medium tier it is expensive, because that tier compares the
workpiece at each index and permuting features changes which material is gone at
that step. The same unrecoverable information costs nothing in one tier and
roughly eight points in another.

### Two questions for the organizers that materially affect our score

The rubric does not define how the medium tier handles a predicted sequence of a
different length from the truth. We assume the strict reading, where an unmatched
operation contributes an intersection over union of zero. Under the alternative
reading, where the comparison truncates to the shorter sequence, the same output
scores 25.33 instead of 23.08 on the same parts. We have implemented both and
report the pessimistic one.

Separately, two of the hard tier sub-tables do not sum to their stated section
budgets. Tool selection is introduced as 20 points but its table awards at most
10. Tool path geometry is introduced as 25 points but its tables sum to 30. We
score the tables as printed and then rescale to the stated section budget, and we
have made that behaviour switchable rather than silent.

## 10. Scientific rigor

The rubric penalises reverse engineering and hacky solutions. We want to be
precise about where we think that line sits and how we stayed on the right side
of it.

The kickoff states the goal is to learn the optimal sequence generated by
deterministic rules inside Siemens NX. So modelling those machining rules, which
is what we do, is the sanctioned target. What would be improper is exploiting the
evaluation harness or the dataset's construction: keying on part identifiers,
fitting to test set artefacts, or gaming the intersection over union with
degenerate meshes. We do none of these. Every input to every model is derived
from the boundary representation, which is what a real user would supply.

### Changes we implemented, measured, and then removed

We think this is the most useful evidence of rigor we can offer, so we list them
completely.

| Change | Why it seemed right | What we measured | Outcome |
|---|---|---|---|
| Split wide-cornered pockets into two operations | Pockets needing more operations had a higher size to corner radius ratio, 4.58 against 3.91 | Marginal count error improved from -0.515 to -0.015, but parts with a wrong count rose from 69 to 86 | Reverted |
| Add a spot drill and drill before every mid-band milled bore | It closes a chain that genuinely occurs in 4.5 percent of holes | Medium fell from 13.33 to 12.08 | Reverted |
| Run the chamfer tool along the edge at mid height | It is the obvious tool motion | Tool paths fell from 1.72 to 1.25 because a 20 millimetre chamfer mill placed on the edge line buries its body in the block | Reverted |
| Round pocket corners using the recognised blend radii | More faithful geometry | Intersection over union moved from 0.8856 to 0.8857 | Kept, but recorded as worthless |
| Bound tool flute length to the cut depth | An 80 millimetre flute on a shallow pocket should over sweep | Exactly neutral, because clipping to the stock already bounds the sweep vertically | Kept, and the neutral result told us the overcut was horizontal, which led to a real bug |
| Extract true pocket outlines instead of bounding boxes | Pockets showed both overcut and undercut, which reads as a wrong shape | 0.97929 to 0.97926, because the outlines are 98 to 100 percent of their bounding box area | Kept, recorded as neutral |
| Model conical bottoms on drilled blind holes | A drill does not leave a flat floor | 0.99295 to 0.99289 | Kept, recorded as neutral |

The recurring failure mode is worth naming. A signal that is real but weak,
applied to every member of a group, fixes the population average and breaks
individual parts. Since the medium tier scores each part independently, matching
a marginal without separating the groups is a net loss. We adopted a rule from
this: a predictor is worth shipping only if it separates the two groups, not if
it merely reproduces their ratio.

### Three of our own conclusions that later measurement refuted

We keep these in the record rather than deleting them, because the reasoning
error is the instructive part.

We claimed that a hole whose diameter exceeds the largest available drill is
milled rather than drilled. It was inferred from eight examples in a validation
listing, and those examples came from parts whose own tool set happened to be
small. Tested properly against 1,120 holes it fails outright: the largest drill in
use is 50 millimetres and every milled hole is between 12.3 and 19.9, so all of
them are inside the drillable range.

We claimed that our generated in-process workpieces scored below raw stock
because of over and under cutting geometry. The observation was real but the
explanation was wrong. Measuring all four cutting policies side by side showed
they span 0.83 points, while sequence length error swings the intersection over
union from 0.998 to 0.445. Geometry was never the dominant term at that stage.

We concluded that some pockets take two operations and that no geometric
predictor separates them. That conclusion was downstream of a bug. A variable in
the feature recogniser shadowed the stock bounds, so most pocket floors were
silently discarded, and the missing floors looked like extra operations. Fixing
one line took pocket count accuracy from 68.0 percent to 98.7 percent and the
overall score up by 8.72 points.

That last one carries a lesson we would apply differently next time. We validated
hole recognition against the published statistics and it passed. We never gave
pockets the same treatment, and a figure of 1.22 recognised floors per part
against a published 1.85 was visible the entire time. When a model fails to find
a signal, the inputs deserve suspicion before the theory does.

## 11. Use of language models, vision models, and pre-trained models

No pre-trained vision or language model contributes to any submitted output.

The two models we ship are trained by us from the competition dataset alone:

* A gradient boosted classifier for hole operation chains, using
  scikit-learn 1.9.0 `HistGradientBoostingClassifier`, trained on 15,734 holes
  from parts numbered below 8,000. Inputs are ten geometric features derived from
  the boundary representation. No pre-training, no external data.
* A gradient boosted classifier for block ordering, same estimator, trained on
  6,985 parts numbered below 8,000, using eleven part level geometric features.

Both are reproducible from the scripts listed in section 7. Neither uses the
rendered images, and neither reads any file that is unavailable at inference
time.

A large language model was used as a coding assistant while developing the
software and while drafting documentation. It did not generate any submitted
easy, medium, or hard output, and no model output is present in any submitted
artefact.

## 12. Future work

In the order we would tackle it, with our reasoning.

**Tool path generation.** This holds 24 of the 25 points we do not have, and the
hard part is already built and validated. What is missing is generating paths
that sweep the right volume: chamfer offset geometry so the conical flank of the
tool lies on the chamfer surface, true pocket outlines for clearing, and
alignment of operations within a hole's chain.

**Pocket identity rather than pocket count.** Our counts are 98.7 percent exact
but a right count with the wrong pocket at a given index still costs a full
feature's volume at that step.

**Augmentation we identified but did not need.** Every prefix of a plan is a
valid machining state, which would turn 10,000 sequences into 91,702 state and
next operation pairs. The stock is a rectangular block, so four rotations and two
mirrors give up to eight label preserving transforms, which we verified is sound
because 97.65 percent of tool blocks carry a single label and reordering within
one cannot change the label sequence.

**The rendered images.** Five renders per part, 50,000 in total, are unused. We
tested whether they could supply what we lack and concluded they cannot. For
every pocket operation with no recognised floor, we checked whether a horizontal
face existed in the boundary representation at the depth the tool reached. All 53
did, with faces as large as 79 by 149 millimetres. The images are lossy
projections of geometry the boundary representation states exactly, so they
cannot contain a feature it does not. They may still be useful as an independent
check on recognition, but they are not a route to the features we were missing.
